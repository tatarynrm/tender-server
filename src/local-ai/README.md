# LocalAiModule — AI-помічник по даних компанії

Корпоративний помічник, який відповідає на питання по базі тендерної платформи. Модель — **Google Gemini** (`LOCAL_AI_PROVIDER=gemini`, дефолт); локальна LLM через LM Studio лишається запасним провайдером і вмикається однією змінною.

Модуль **не замінює і не чіпає** наявний `src/ai/` (Gemini для Telegram-бота й пошти) — це окремий контур зі своїми промптами, сесіями й правами. Спільний у них лише ключ `GEMINI_API_KEY`.

> Історична назва `local-ai` збережена: її знають маршрути `/local-ai/*`, фронт і `LOCAL_AI_ALLOWED_EMAILS`. Перейменування зачепило б більше, ніж дало б.

## Що вміє зараз

Чат із моделлю по даних компанії. **Єдине джерело — Postgres**; Oracle вимкнено (`LOCAL_AI_ORACLE_ENABLED`, дефолт `false`).

| Функція (tool) | Джерело | Доступ |
|---|---|---|
| `runSqlQuery` | Postgres, **SQL пише модель по всій схемі** | ICT / admin |
| `getOrders` `generateReport` `searchDocuments` | Postgres, фіксовані SELECT-и | усі |
| `getTripsReport` `getTruckLocation` `getDriverStatus` `getClientDebt` | Oracle `ZAY` / `AVRMONCLIENT` | **вимкнені** |

Oracle-tools не реєструються взагалі, поки джерело вимкнене: показувати моделі функцію, яка гарантовано впаде, гірше за її відсутність.

## Як це працює

```
React (/log/ai)
   ↓ POST /local-ai/chat  (кука centrifuge)
LocalAiService
   ├─ 1. роутер:      модель обирає tool + аргументи (JSON-схема)
   ├─ 2. ToolRegistry: перевірка існування tool і прав користувача
   │      ├─ фіксовані tools → SELECT із коду, значення біндами
   │      └─ runSqlQuery → SqlGeneratorService (модель пише SELECT по каталогу схеми)
   │           └─ SqlGuardService  → лише SELECT, whitelist таблиць, LIMIT
   │                └─ ReadOnlyQueryService → READ ONLY-транзакція + statement_timeout
   │                     └─ Postgres
   └─ 3. форматування: модель переказує отримані рядки українською
```

## Провайдер моделі

Уся решта модуля залежить від інтерфейсу [LlmClient](llm/llm-client.interface.ts) (токен `LLM_CLIENT`), а конкретний клас обирається в [local-ai.module.ts](local-ai.module.ts):

| `LOCAL_AI_PROVIDER` | Клас | Куди йдуть дані |
|---|---|---|
| `gemini` (дефолт) | [GeminiClient](llm/gemini.client.ts) | хмара Google |
| `lmstudio` | [LmStudioClient](lm-studio/lm-studio.client.ts) | локальна мережа |

Обраний провайдер пишеться в лог на старті й віддається у `GET /local-ai/health` полем `provider` — фронт показує його в шапці чату.

**Маршрутизація йде через JSON-схему, а не native tool calling**, хоча Gemini його вміє: схема працює однаково в обох провайдерів, і повернення на локальну модель (де параметр `tools` просто ігнорується) не потребує другої гілки коду.

Одна особливість Gemini закріплена в [ROUTER_SCHEMA](local-ai.constants.ts): `args` — це **рядок із JSON**, а не вкладений обʼєкт. Gemini вимагає перелічити властивості кожного `OBJECT` у `responseSchema`, а набір аргументів у кожного tool свій; `LocalAiService.parseArgs` розбирає рядок і терпимо приймає також готовий обʼєкт.

Токени «роздумів» (thinking) списуються з `maxOutputTokens`, тому за замовчуванням вимкнені (`LOCAL_AI_GEMINI_THINKING_BUDGET=0`) — інакше модель встигала б подумати й обірватися на півслові. Для складніших звітів бюджет можна підняти.

## Що бачить модель: уся схема бази

`SchemaCatalogService` на старті (і на `POST /local-ai/schema/refresh`) читає з живої бази:

- **усі таблиці й представлення схеми `public`** — крім `DENIED_TABLE_PATTERNS`;
- колонки, типи, `COMMENT ON TABLE/COLUMN` (у нашій базі коментарі українські, тож описи дістаються безкоштовно);
- первинні ключі;
- **звʼязки**: зовнішні ключі з `pg_constraint` плюс здогади за назвами колонок (`id_company` → `company.id`) — у промпті вони позначені `FK` і `~` відповідно, бо FK у базі стоять не скрізь.

На дев-базі це 81 таблиця, ~596 колонок і 75 звʼязків — близько 31 тис. символів (~10 тис. токенів) на промпт генератора SQL.

Поверх інтроспекції лягає [postgres.catalog.ts](schema/postgres.catalog.ts) — **шар сенсу, а не список доступу**: описи найуживаніших таблиць, значення статусів, готові JOIN-и, правила предметної області і приклади «питання → SQL». Ці таблиці йдуть у промпті першими. Файл же лишається резервом: якщо база недоступна на старті, помічник працює зі статичним каталогом.

Наслідок: **нова таблиця в базі стає видимою моделі без правки коду**, а закрити щось можна лише через `DENIED_TABLE_PATTERNS` / `HIDDEN_COLUMN_PATTERNS`.

Каталог у поточному стані видно через `GET /local-ai/schema`.

### Що приховано від моделі

| Фільтр | Що ховає |
|---|---|
| `DENIED_TABLE_PATTERNS` | `usr`, `usr_pre_register` (там `password_hash`), сесії, міграції, `pg_*` |
| `HIDDEN_COLUMN_PATTERNS` | `migrate_*`, `*_uk`, `url`, `key`, `private_info`, `gps_*`, `password*`, `ipn`, `*token*` |
| `SqlGuardService.ALWAYS_DENIED` | те саме по таблицях, другим рубежем |
| `SqlGuardService.DENIED_COLUMNS` | `private_info`, `password`, `password_hash`, `ipn` — навіть у дозволених таблицях |

Приховане в промпті — це прохання; заборонене у валідаторі — це обмеження. Тому обидва списки ведуться паралельно.

## Генерація SQL моделлю (`runSqlQuery`)

Для типових питань лишаються фіксовані tools — вони швидші й передбачувані. `runSqlQuery` покриває все інше: нестандартні зрізи по будь-яких таблицях бази.

Модель отримує повну схему і повертає JSON `{sql, explanation}`. Якщо запит не пройшов валідатор або впав у БД, помилка йде назад у модель і вона робить **одну** спробу виправлення (`MAX_ATTEMPTS = 2`). Згенерований SQL повертається на фронт у `meta.generatedSql` — користувач має бачити, звідки взялися цифри.

**Псевдоніми колонок — українською в подвійних лапках** (`AS "Кількість тендерів"`): ключі рядків стають заголовками таблиці під відповіддю, тому латиниці там бути не повинно. Технічні ідентифікатори (`id`, `id_*`, `ids_*`) у вибірку не потрапляють, якщо користувач не попросив їх прямо. Те саме правило застосоване до фіксованих tools, а фронт про всяк випадок ховає id-колонки й перекладає відомі латинські назви — в історії лишилися старі відповіді.

Через українські псевдоніми валідатор знімає **спершу подвійні лапки, потім одинарні**: апостроф у назві (`AS "Обʼєм"`, `AS "Ім'я"`) інакше відкрив би неіснуючий рядковий літерал і завалив би нормальний запит.

Доступ — лише ICT та адміністратори: довільна вибірка по всій схемі показала б перевізнику ставки конкурентів.

### Заборонено все, крім SELECT

`SqlGuardService` — головний рубіж, і він же покритий тестами (`sql-guard.service.spec.ts`, 30 кейсів):

| Правило | Що відхиляється |
|---|---|
| лише `SELECT` | запит мусить починатися з `SELECT` |
| мутації й DDL | `INSERT INTO`, `DELETE FROM`, `UPDATE … SET`, `MERGE INTO`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `GRANT`… |
| одна інструкція | `SELECT 1; DROP TABLE …` |
| без коментарів | `--`, `/* */` — класичний спосіб сховати хвіст запиту |
| без блокувань | `FOR UPDATE`, `FOR SHARE` |
| без `SELECT … INTO`, `RETURNING`, `$$` | створення таблиць і тіла анонімних блоків |
| whitelist таблиць | усе, чого немає в каталозі схеми |
| чорний список | `usr`, `session`, `information_schema`, `pg_catalog`, будь-що з префіксом `pg_` |
| приватні колонки | `private_info`, `password_hash`, `ipn` — навіть у дозволених таблицях |
| побічні ефекти | `set_config`, `nextval`, `dblink`, `lo_import`… |
| ліміт рядків | `LIMIT` дописується або зрізається до `LOCAL_AI_MAX_ROWS` |

Перевірка йде по запиту **зі знятими рядковими літералами**: пошук `ILIKE '%delete from%'` — це дані, а не команда, і відхиляти його не можна. Одинока лапка після зняття означає незакритий літерал і теж відхиляється.

Так само команди шукаються разом із продовженням (`DELETE FROM`, а не голе `DELETE`): відколи модель бачить усю схему, у запит легально потрапляють колонки `comment`, `notify`, `copy` і функція `replace()` — пословний блек-лист відхиляв би нормальні вибірки.

`set_config` у списку не випадково: `SELECT set_config('statement_timeout','0',false)` формально не пише даних, проходить READ ONLY-транзакцію, переживає `ROLLBACK` і лишається на зʼєднанні, яке повертається в **спільний** `PG_POOL`.

Далі — READ ONLY-транзакція зі `statement_timeout`: СУБД сама відхиляє запис. Кожен запит — і виконаний, і відхилений — потрапляє в лог.

### Рубежі захисту SQL

1. **Промпт** — модель знає межі й не витрачає спробу на відмову.
2. **SqlGuardService** — правила з таблиці вище.
3. **READ ONLY-транзакція** зі `statement_timeout` — СУБД сама відхиляє запис.

Четвертий рубіж із ТЗ — окремий користувач БД `postgres_ai_reader` з правом лише `SELECT` — **поки не заведений**: `ReadOnlyQueryService` бере той самий `PG_POOL`, що й решта застосунку. Коли такий користувач зʼявиться, під нього потрібен окремий пул, а не зміна цього коду.

## Хто має доступ

Модуль у дослідній експлуатації, тому доступ **поіменний**, а не за роллю: модель бачить усю схему тендерної платформи, пише SQL сама, а запити йдуть у хмару Google.

`LOCAL_AI_ALLOWED_EMAILS` перевіряє [LocalAiAccessGuard](guards/local-ai-access.guard.ts). Він висить на **всьому контролері** через декоратор `@LocalAiAccess()` — так новий ендпоінт не може випадково лишитися відкритим. Гард fail-closed: немає користувача в запиті — 403.

Декоратор навмисно збирає `UseGuards(AuthGuard, LocalAiAccessGuard)` одним масивом: гард читає `request.user`, який кладе AuthGuard, а при двох окремих декораторах порядок залежав би від того, як їх переставлять у файлі.

На фронті пункт меню й сторінка `/log/ai` сховані тим самим списком у [client-ai/src/shared/constants/local-ai.ts](../../../client-ai/src/shared/constants/local-ai.ts) — це лише UI-гейт, справжня перевірка тут. Списки треба тримати однаковими.

## Ендпоінти

Усі під `@LocalAiAccess()` — кука `centrifuge` плюс перевірка пошти.

```
GET    /local-ai/health                  провайдер, модель, функції, стан каталогу схеми
GET    /local-ai/schema                  таблиці, колонки і звʼязки, які бачить модель
POST   /local-ai/schema/refresh          перечитати схему з БД
GET    /local-ai/sessions?limit=&offset= сторінка списку розмов (total, hasMore)
POST   /local-ai/sessions                нова розмова
GET    /local-ai/sessions/:id/messages   історія
PATCH  /local-ai/sessions/:id            перейменувати
DELETE /local-ai/sessions/:id            видалити одну розмову
DELETE /local-ai/sessions                видалити всі розмови користувача
POST   /local-ai/chat                    { text, sessionId? }
```

## Історія чату

Живе в **Redis** (`ai:sessions:*`, `ai:session:*`, `ai:messages:*`) з TTL, бо схему Postgres у цьому проєкті ми не змінюємо.

Доступ іде через інтерфейс `ChatHistoryStore`. Коли зʼявляться процедури `ai_session_*`, достатньо додати другу реалізацію і підмінити клас у `local-ai.module.ts` — `LocalAiService` не змінюється.

### Скільки це важить у памʼяті

Разом із відповіддю зберігається до 50 рядків таблиці даних, тому одна розмова — це десятки кілобайт у Redis, який тримає все в RAM. Звідси три обмеження:

- **`LOCAL_AI_MAX_SESSIONS` (50)** — стеля розмов на користувача. Найстаріші за `updatedAt` видаляються повністю, разом із повідомленнями (`trimOldSessions`); зачистка йде при створенні сесії і при читанні ПЕРШОЇ сторінки списку — на другій і далі вона нічого б не змінила, зате додавала б рейс до Redis на кожен скрол.
- **`LOCAL_AI_HISTORY_MAX_MESSAGES` (200)** — хвіст повідомлень усередині розмови (`LTRIM`).
- **`DELETE /local-ai/sessions`** — ручне очищення всієї історії з UI.

Сесія створюється **лише разом із першим повідомленням**: кнопка «Нова розмова» на фронті просто чистить екран. Інакше кожен її клік займав би слот у ліміті й витісняв найстарішу справжню переписку порожньою.

Стеля віддається на фронт у `GET /local-ai/health` (`limits.maxSessions`) — щоб число «50» не дублювалося константою в React.

Сам список фронт вантажить сторінками по 20: панель показує десяток рядків, і тягнути всі 50 разом із метаданими заради неї немає сенсу. Сторінка читається одним `MGET` замість N окремих `GET`, а видалення (одної розмови, старого хвоста чи всієї історії) — одним `DEL` на всі ключі плюс один `ZREM`: при очищенні півсотні розмов це 2 рейси до Redis замість 150.

Якщо `POST /local-ai/chat` отримав `sessionId` неіснуючої розмови (її витіснив ліміт або зʼїв TTL), діалог не обривається — сервер заводить нову сесію і ставить у відповіді `sessionReplaced: true`, а фронт показує про це тост.

## Запуск

```powershell
# 1. Інфраструктура
cd server-ai; docker compose up -d db redis

# 2. Бекенд і фронт
cd server-ai; npm run start:dev
cd client-ai; npm run start:dev
```

Сторінка — `/log/ai` (простір менеджерів ICT). Перевірити стан моделі без фронта — `GET /local-ai/health`.

Для провайдера `lmstudio` додатково: LM Studio → Developer → Start Server (порт 1234), перевірка `curl http://localhost:1234/v1/models`.

## Чого ще немає

- завантаження й розбір документів (PDF / DOCX / XLSX / зображення) — на бекенді вже є `pdf-parse`, `xlsx`, `exceljs`, `sharp`; бракує `mammoth` для DOCX;
- голос: Gemini вміє транскрибувати аудіо (див. `AiService.transcribeVoice`), у помічник це ще не заведено;
- експорт звітів в Excel / PDF — генератори вже є у `src/telegram/report-file.service.ts`, їх можна перевикористати;
- окремий користувач БД `postgres_ai_reader`;
- MCP-сервери;
- ролі `ACCOUNTANT` / `DISPATCHER` — у системі зараз лише `is_admin` / `is_ict` / `is_manager`, нові ролі потребують змін у БД, які веде окремий розробник.
